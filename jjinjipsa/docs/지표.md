# 지표 — 무엇을 보고 무엇으로 판단하는가

지시서 Phase 4("리텐션을 확인하고 수익화")가 지정한 숫자를 보기 위한 문서다.
구현은 `lib/analytics.ts`(수집) + `supabase/migrations/0008_analytics_events.sql`(저장),
집계는 Supabase SQL Editor에서 **직접** 한다. 대시보드 도구를 붙이지 않는다.

## 왜 외부 분석 도구를 안 쓰나

1. 이미 Supabase를 쓰고 있어서 테이블 하나면 된다.
2. 이 앱이 다루는 것은 고양이 건강 기록이다. 누가 언제 어떤 증상을 기록했는지의
   행동 로그를 제3자 서버로 넘길 이유가 없다.
3. 개인정보 원칙(원본 IP 미저장 등)을 그대로 이어갈 수 있다.

## 무엇을 저장하지 않나

**본문은 저장하지 않는다.** 고양이 이름·메모·질문·태그 이름이 들어가지 않는다.
`lib/analytics.ts`가 이벤트 이름과 props 키를 화이트리스트로 막고, 값도
숫자·불리언·짧은 ASCII 슬러그(`a-z0-9_-`, 24자)만 통과시킨다 — 한글 본문은
규격상 통과할 수 없다. `npm run test:analytics`가 이걸 검사한다.

## 읽을 때 알고 있어야 할 한계

- **익명 계정은 기기 단위다.** 로그인 전 사용자는 브라우저마다 다른 uid를 갖는다.
  기기를 바꾸거나 브라우저 데이터를 지우면 다른 사람으로 잡힌다.
  → 리텐션은 **로그인 계정만** 보는 쿼리를 따로 둔다 (아래 D1/D7).
- **`day`는 로컬 날짜다** (클라이언트가 채운다). `created_at`은 UTC 시각이다.
  한국 기준 하루로 세려고 이렇게 나눴다.
- **전송 실패는 조용히 버린다.** 지표 때문에 화면이 멈추면 안 되므로,
  오프라인·차단 환경의 이벤트는 유실된다. 절대값이 아니라 비율로 읽는다.
- 테스터(개발자 본인) 계정이 섞여 있다. 초기에는 표본이 작아 한두 명이 비율을
  흔든다 — 며칠치를 모아 보고, 한 자릿수 표본으로 결론을 내지 않는다.

| 이름 | 언제 | props | 답하는 질문 |
|---|---|---|---|
| `app_open` | 앱 진입 (하루 1회) | — | 리텐션의 분모 |

| `symptom_saved` | 증상 기록 저장 | `tags`, `memo`, `from`(quick·direct) | 이상 기록 사용량, 홈 Quick Action 효과 |

## KPI 쿼리

SQL Editor(service_role)에서 실행한다. 앱에는 읽기 정책이 없어 클라이언트로는
남의 로그를 못 읽는다.

### 0. 오늘 잘 들어오고 있나 (연결 확인)

```sql
select name, count(*) as n, max(created_at) as last_at
from public.analytics_events
where day >= current_date - 7
group by name
order by n desc;
```

### 1. D1 / D7 리텐션

가입일(=첫 `app_open`) 기준 코호트. **정식 계정만** 본다 — 익명 uid는 기기 단위라
리텐션이 실제보다 낮게 나온다.

```sql
with real_users as (
  select id from auth.users where is_anonymous = false
),
opens as (
  select e.user_id, e.day
  from public.analytics_events e
  join real_users u on u.id = e.user_id
  where e.name = 'app_open'
  group by 1, 2
),
first_day as (
  select user_id, min(day) as d0 from opens group by 1
)
select
  f.d0                                                         as 가입일,
  count(distinct f.user_id)                                    as 코호트,
  count(distinct o1.user_id)                                   as d1_잔존,
  round(100.0 * count(distinct o1.user_id)
        / nullif(count(distinct f.user_id), 0), 1)             as d1_퍼센트,
  count(distinct o7.user_id)                                   as d7_잔존,
  round(100.0 * count(distinct o7.user_id)
        / nullif(count(distinct f.user_id), 0), 1)             as d7_퍼센트
from first_day f
left join opens o1 on o1.user_id = f.user_id and o1.day = f.d0 + 1
left join opens o7 on o7.user_id = f.user_id and o7.day = f.d0 + 7
group by f.d0
order by f.d0 desc;
```

> 지시서 기준선: **D1 40% / D7 20%**. 아래로 크게 밑돌면 기능을 더 얹기 전에
> 첫 3일에 무슨 일이 벌어지는지부터 본다.

### 2. 오늘냥 기록률 — 앱을 연 날 중 상태를 기록한 날

```sql
select
  day                                                          as 날짜,
  count(distinct user_id) filter (where name = 'app_open')      as 접속자,
  count(distinct user_id) filter (where name = 'daily_status_saved') as 기록자,
  round(100.0 * count(distinct user_id) filter (where name = 'daily_status_saved')
        / nullif(count(distinct user_id) filter (where name = 'app_open'), 0), 1) as 기록률
from public.analytics_events
where day >= current_date - 30
group by day
order by day desc;
```

4항목을 **끝까지** 채우는지는 따로 본다 (`items` 최댓값이 4인 사람 비율):

```sql
select day,
       count(*) filter (where max_items >= 4) as 네개_다,
       count(*)                               as 기록자
from (
  select user_id, day, max((props->>'items')::int) as max_items
  from public.analytics_events
  where name = 'daily_status_saved' and day >= current_date - 30
  group by 1, 2
) t
group by day order by day desc;
```

### 3. 주간 기록 일수 — 한 사람이 일주일에 며칠 기록하나

```sql
select
  date_trunc('week', day)::date                as 주,
  round(avg(days), 2)                          as 평균_기록일,
  count(*)                                     as 사용자수,
  count(*) filter (where days >= 3)            as 주3일이상
from (
  select user_id, date_trunc('week', day) as w, day,
         count(distinct day) over (partition by user_id, date_trunc('week', day)) as days
  from public.analytics_events
  where name = 'daily_status_saved' and day >= current_date - 56
) t
group by 1
order by 1 desc;
```

### 4. 냥박사 재사용률 — 한 번 써 본 사람이 다시 오나

```sql
with per_user as (
  select user_id,
         count(*)            as 질문수,
         count(distinct day) as 질문한_날
  from public.analytics_events
  where name = 'chat_asked' and day >= current_date - 30
  group by 1
)
select
  count(*)                                   as 써본_사람,
  count(*) filter (where 질문한_날 >= 2)      as 이틀이상_쓴_사람,
  round(100.0 * count(*) filter (where 질문한_날 >= 2)
        / nullif(count(*), 0), 1)            as 재사용률,
  round(avg(질문수), 1)                       as 인당_평균질문
from per_user;
```

질문이 어디서 시작되는지 (추천 질문이 일하고 있나):

```sql
select props->>'source' as 출발점, count(*) as n
from public.analytics_events
where name = 'chat_asked' and day >= current_date - 30
group by 1 order by n desc;
```

### 5. 증상 기록 → 냥박사 연결률 (핵심 루프)

```sql
select
  day                                                        as 날짜,
  count(*) filter (where name = 'symptom_saved')             as 증상기록,
  count(*) filter (where name = 'symptom_to_chat')           as 상담으로_이어짐,
  round(100.0 * count(*) filter (where name = 'symptom_to_chat')
        / nullif(count(*) filter (where name = 'symptom_saved'), 0), 1) as 연결률
from public.analytics_events
where day >= current_date - 30
group by day order by day desc;
```

홈 Quick Action이 기록을 만들어 내는지:

```sql
select props->>'from' as 진입경로, count(*) as n
from public.analytics_events
where name = 'symptom_saved' and day >= current_date - 30
group by 1;
```

### 6. 주간 리포트 조회율

```sql
select
  date_trunc('week', day)::date                                       as 주,
  count(distinct user_id) filter (where name = 'app_open')             as 접속자,
  count(distinct user_id) filter (where name = 'weekly_report_viewed') as 조회자,
  round(100.0 * count(distinct user_id) filter (where name = 'weekly_report_viewed')
        / nullif(count(distinct user_id) filter (where name = 'app_open'), 0), 1) as 조회율
from public.analytics_events
where day >= current_date - 56
group by 1 order by 1 desc;
```

빈 리포트를 열게 하고 있지는 않은지 (`days`가 작은 조회가 많으면 노출 조건을 올린다):

```sql
select (props->>'days')::int as 기록일, count(*) as 조회수
from public.analytics_events
where name = 'weekly_report_viewed' and day >= current_date - 30
group by 1 order by 1;
```

### 7. 생활기록부 초안 — 요청 대비 적용

```sql
select
  count(*) filter (where name = 'report_draft_requested') as 요청,
  count(*) filter (where name = 'report_draft_applied')   as 적용,
  round(100.0 * count(*) filter (where name = 'report_draft_applied')
        / nullif(count(*) filter (where name = 'report_draft_requested'), 0), 1) as 적용률
from public.analytics_events
where day >= current_date - 30;
```

적용률이 낮으면 초안 품질 문제거나, 근거 검증(`/api/report-draft`의 3중 검증)이
너무 많이 걸러내고 있는 것이다. `report_draft_requested`의 `texts` 분포를 같이 본다.

### 8. 공유 카드 / 양치 챌린지

```sql
select name, props->>'kind' as 종류, props->>'streak' as 연속,
       count(*) as n
from public.analytics_events
where name in ('share_card_saved', 'brush_milestone_shown')
  and day >= current_date - 30
group by 1, 2, 3 order by n desc;
```

## 운영

- **테이블 정리:** 이벤트는 계속 쌓인다. 분석에 90일이면 충분하므로 주기적으로 지운다.

  ```sql
  delete from public.analytics_events where day < current_date - 90;
  ```

- **탈퇴한 사용자:** `user_id`는 `on delete set null`이라 계정을 지우면 로그는
  주인 없는 행으로 남는다 (본문이 없으므로 개인을 식별하지 않는다).
  완전히 지우려면 위 정리 쿼리에 `or user_id is null`을 더한다.
- **새 이벤트를 더할 때:** `lib/analytics.ts`의 `EVENT_NAMES`·`PROP_KEYS`에 먼저
  추가하고, "이 값으로 개인을 특정할 수 있나"를 확인한 뒤,
  `scripts/test-analytics.mjs`의 `USED_IN_APP`에도 넣는다.
